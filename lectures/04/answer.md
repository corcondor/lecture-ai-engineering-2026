# 第4回 解答

## 宿題

- 取り組んだレベル：発展
- 調査対象：SWE-bench Verified
- 調査日：2026年11月15日
- データセット：[princeton-nlp/SWE-bench_Verified](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified)
- 問題閲覧：[Dataset Viewer](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified/viewer/default/test)

### やったこと

公開データセットと元の GitHub issue を対応させ、Astropy の3件について、要求される修正、難しさ、取り組む場合の方針を整理した。さらに、作成・検証の分担と採点方法を公式資料で調べ、講義の10件の評価セットと比較した。調査と文章整理に生成AIを利用し、参照した一次資料を併記した。

### 読んだ問題と難しさ

#### 1. astropy__astropy-12907：入れ子になったモデルの独立性

元の問題：[astropy/astropy #12906](https://github.com/astropy/astropy/issues/12906)

複数のモデルを並べて結合した場合と、一部を先に結合して入れ子にした場合で、入出力の依存関係を表す行列が変わってしまう問題である。本来独立な線形モデル同士が、入れ子にすると依存していると判定される。

難しいのは、目に見える行列の値を直すだけではなく、モデルの結合構造と依存関係の伝播を理解する必要がある点である。LLMも、提示された例だけに合わせた修正では、別の組み合わせや深い入れ子を壊す可能性がある。

取り組むなら、平坦な結合と入れ子の結合を最小例で比較し、既存の依存関係を保持すべき処理を追う。深さやモデルの種類を変えても同じ意味の結合が同じ結果になることをテストしたい。

#### 2. astropy__astropy-13033：必須列が欠けたときの例外メッセージ

元の問題：[astropy/astropy #13009](https://github.com/astropy/astropy/issues/13009)

TimeSeries に time 以外の必須列を設定してからその列を削除すると、欠けた列を説明せず、time が先頭にあるにもかかわらず先頭列を問題視する紛らわしい例外が出る。求められるのは、実際の違反内容に合った例外を返すことである。

見かけ上は文字列の修正でも、必須列不足と列順序の違反を区別する必要がある。LLMが一つの例外文だけを置き換えると、ほかの不正な状態を誤って説明するおそれがある。

取り組むなら、必須列の有無、数、順序を別々に確認し、欠落と順序違反の両方をテストする。修正方針は比較的立てやすいが、既存APIの振る舞いを維持する確認は必要になる。

#### 3. astropy__astropy-13453：HTML出力で列の書式指定が無視される

元の問題：[astropy/astropy #13451](https://github.com/astropy/astropy/issues/13451)

表をHTMLへ出力すると、数値の表示形式を指定する formats 引数が反映されない。同じ指定はCSVなどでは機能しており、HTMLでも指定した表示になることが期待されている。

難しいのは、表示結果だけでなく、共通の表処理とHTML専用処理のどこで書式指定が失われるかを特定する点である。LLMがHTML出力だけに場当たり的な処理を加えると、既存の書式処理と重複したり、型の違いで挙動が変わったりする可能性がある。

取り組むなら、CSVとHTMLの処理経路を比較し、共通の書式処理を利用できるか確認する。数値の科学表記に加え、書式指定なし、文字列列、複数列でも期待する出力になるかを検証したい。

これらは修正・実行の成績ではなく、問題を読んで整理した解法方針と難しさである。3件とも同じライブラリから選んだため、ベンチマーク全体の難度分布を代表するとは限らない。

### 作成に関わった人と検証手順

元の問題は、12のPython OSSリポジトリにある解決済みissueと修正PRに由来する。問題の報告者・修正者と、Verified化の品質検証者は分けて考える必要がある。93人という人数は、Python経験のある検証担当開発者の人数であり、500問を新たに作問した人数ではない。

公式説明では、1,699件を対象に各件を独立した3人が確認した。問題文の明確さや採点テストの妥当性を評価し、3人のうち最も厳しい判定を採用して不適切なものを除外した。68.3%が除外され、残った候補から難度にも配慮して500件を構成した。元のissue報告者やPR作成者の総人数は、この公式説明からは特定できない。

出典：[OpenAI, Introducing SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)

### 採点方法

モデルは問題文と修正前のリポジトリから修正パッチを作る。採点は文章の印象をLLMに判断させる方式ではなく、コードのテスト実行で行う。

- FAIL_TO_PASS：修正前には失敗し、適切な修正後には成功するテスト。
- PASS_TO_PASS：修正前後とも成功すべき既存機能の回帰テスト。

両方を満たす必要がある。ただし、テストが通ることと、問題文から期待される正しさが完全に一致するとは限らない。

出典：[OpenAIの評価方法の説明](https://openai.com/index/introducing-swe-bench-verified/)

### 講義の評価セットとの違い

| 観点 | 講義の評価セット | SWE-bench Verified |
|---|---|---|
| 目的 | 学習支援エージェントの回答を、採点器が適切に判断できるか確かめる | 既存コードの不具合を修正できるか測る |
| 規模・起源 | 講師が準備した質問・回答10件。正常系とエッジケース、一部の意図的な失敗を含む | 実際のOSS issue・PRをもとに選別した500件 |
| 品質の確認 | 受講者・講師のラベルとLLM判定を比較し、不一致や要確認を検討する | 専門の開発者が問題文とテストを複数人で事前確認する |
| 採点 | 根拠・範囲・ヒント・分かりやすさは人とLLM。回の表示はコード | 修正対象と回帰防止のテストを実行する |
| 曖昧さへの対応 | unsureを自動判定から外し、基準を具体化して再評価する | 曖昧な問題や不適切なテストを選別段階で除く |
| 残る課題 | 小規模で、基準の主観性や講師・受講者の判断差がある | テストの網羅性・仕様とのずれ、公開問題の学習データ混入がある |

講義の手順：[第4回の問題文](https://github.com/matsuolab/lecture-ai-engineering-2026/blob/main/lectures/04/problem.md)

### 気づき・疑問

共通するのは、評価対象の性能を論じる前に「採点の基準が妥当か」を確かめる必要がある点である。講義では人とLLMの不一致を調べる。コード課題ではテストが客観的に見えても、問題文にない条件を要求したり、正しい別解を落としたりし得る。複数人の検証は重要だが、それだけで評価の妥当性が永久に保証されるわけではない。

2026年2月23日のOpenAIの再検証では、モデルが安定して解けなかった138件を監査し、その59.4%に問題文やテスト設計上の問題があると報告した。これは500件全体からの無作為抽出による割合ではない。また公開問題・解答の学習データ混入を指摘し、同社はVerifiedのスコア報告を停止した。したがって、今回は評価設計の具体例として調査し、現在のフロンティア性能を十分に表す指標とは扱わない。

出典：[OpenAI, Why we no longer evaluate SWE-bench Verified](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)

評価セットを改善するなら、正解パッチとの一致を目的にせず、仕様を満たす別解も通るテストにすること、評価に使わない新しい問題で改訂の効果を確認すること、失敗例を人が継続的に見直すことを重視したい。
